# Provider ownership security rollout (OPH-3 / OPH-9 / OPH-14)

## Verified production context and findings

The owner confirmed Supabase project `aziibxfjoduwwkmcczrm` (`ohio-parent-hub`) on October 14, 2026. Read-only inspection found the same profile columns, primary/unique ownership constraints, RLS policies and broad anon/authenticated grants as the checked-in schema. `verified` defaults to true. The only custom profile trigger updates timestamps; no custom Auth-user trigger creates profiles. Production Postgres is 17.6.1.084; the isolated CLI stack uses 17.6.1.106.

The local baseline reproduced an authenticated owner changing subscription status and Stripe customer ID directly through the Data API. No such write was attempted in production. Live policies and grants permit the same category of write; this change prevents it once its migration is applied. Current production migration history contains only `20260504162054_jobs_hub`; the initial schema and claim simplification appear to have been applied outside that history. **Do not blindly run `supabase db push --linked`**, which could attempt to recreate existing tables/types from 001–003. Review/reconcile migration history separately, or apply only the new reviewed migration through the intended project's migration mechanism.

## Behavior after the change

- Clients can read only their own profile and update only their own `display_name`. They cannot insert/delete profiles, change listing ownership, verified status, profile email, timestamps or billing fields. Both table-level and explicit column-level privileges are removed before granting the allowed operations. RLS remains enabled.
- Server-only claim completion fetches the user from Auth, requires a confirmed, non-anonymous email and matches it against the authoritative directory email. A metadata program number is a lookup hint, not authorization. The callback, token-hash confirmation and dashboard fallback all use this verifier.
- Established verified profiles retain ownership and billing state even when user metadata or directory emails change. New claims use INSERT rather than upsert; the existing unique constraints resolve races without transferring ownership. Repeated successful callbacks are idempotent for the same owner. Nonverified existing profiles require support rather than being silently promoted.
- Signup uses the cookie-based public Auth client so email confirmation and PKCE code exchange share the verifier. Service-role clients do not persist Auth sessions. Promo metadata remains supported but does not establish ownership.
- Errors return an explicit claim failure and a useful login-screen message; database failure never becomes a successful claim. Recovery tokens still go to password reset. External callback redirect destinations are rejected.
- Trusted server claim inserts and Stripe persistence still use service-role access. Premium subscription policies and webhook retry behavior remain OPH-4/5/6 and OPH-15.

## Tests and their boundaries

`npm run test:integration` now covers actual anon/authenticated Data API permissions, allowed display-name edits, protected-field denial, profile insert/delete denial, cross-owner private profile/listing/job access and mutation denial, valid own-content edits and service-role billing persistence. Auth tests exercise real local signup, captured email, PKCE exchange, token-hash verification, token replay, unconfirmed sessions, mismatched/direct signup, metadata changes, concurrent completion, existing ownership conflicts, dashboard fallback, recovery and persistence errors.

These Node tests invoke the real server actions and route handlers. They replace the authoritative directory lookup with synthetic `@example.test` records and provide real local cookie-based Auth clients in place of Next's request cookie context. Only the persistence-failure test injects a failed INSERT. Database permission assertions always use real client roles. There is no production fixture/data override, production test email or service-role-only authorization assertion.

Playwright additionally exercises the built app's login/dashboard rejection path with a synthetic account pointing at a real public program number, normal existing-owner sign-in, and visible persistence-error guidance in desktop/mobile Chromium. The existing public discovery tests continue to run. All tests are part of the existing required-check recommendation, `Regression suite`; no checks are skipped to hide an ownership failure.

## Rollout and rollback

1. Review the exact PR commit and its isolated CI results. Verify a clean local `test:reset` applies all migrations and the tests pass. Check Supabase security advisors locally.
2. Use a confirmed nonproduction Supabase project to confirm email confirmation is enabled (auto-confirmed signup must not be allowed), then validate email templates/redirect allowlists and signup confirmation, established-owner login, claim failure messages and trusted billing writes with the actual deployment configuration. No separate hosted staging project has been confirmed yet. The connector does not expose hosted Auth configuration; email-confirmation settings/templates still require checking before release. Vercel previews may point at production services; public read-only smoke checks are safe, but do not create real claims, send real mail or exercise payments there as tests.
3. Deploy the reviewed application verification paths before tightening profile grants, or coordinate a staged app deployment with the migration. The new application is compatible with both old and new grants; tightening grants while the old app is running breaks its client callback writes and leaves its service-role dashboard bypass open until the app is replaced. Keep the interval between reviewed app release and migration short; the direct API protection is not active until migration success.
4. Apply **only** `20261014194922_protect_profile_ownership.sql` to confirmed project `aziibxfjoduwwkmcczrm` through a reviewed migration operation. It changes privileges/defaults/policies and the timestamp function search path; it does not rewrite existing owner rows or Stripe state. Take/confirm a backup and record migration/deployment identities before release. Re-inspect effective grants (including inherited/column privileges), policies/defaults and unique constraints afterward.
5. Run read-only public production smoke checks and confirm the release commit owns the intended domain. Check signup/error/Stripe persistence logs without exposing credentials or user data. Avoid synthetic production users or charges.
6. Preserve the hardened grants on rollback. Do not re-enable protected-field client writes, restore `verified=true` as the default, or roll back to application code that trusts user metadata. A safe rollback/forward repair must keep the trusted verifier compatible with the hardened database. Application rollback does not restore database grants or Stripe state.

No hosted database write is included in local development or CI. The migration and application rollout require review together; merging code alone does not apply the production database protection. Never treat PR preview/CI success as evidence that the hosted migration has been applied.
